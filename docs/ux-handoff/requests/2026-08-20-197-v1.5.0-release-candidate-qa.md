# UX Handoff 197 - FamilyHub v1.5.0 Release Candidate QA

Data: 2026-08-20  
Priorita: alta  
Tipo: validazione release, nessuna nuova API

## Obiettivo

Validare in modo asincrono il frontend dei moduli consegnati negli handoff `188-196` prima della pubblicazione di FamilyHub `v1.5.0`.

## Baseline da usare

- branch di preparazione: `release/v1.5.0`;
- versione attesa in `frontend/package.json`: `1.5.0`;
- contratto API: `docs/api/openapi.yaml`;
- checklist vincolante: `docs/qa/2026-08-20-v1.5.0-uat-checklist.md`;
- questa richiesta non autorizza modifiche ai contratti API.

## Attivita UX obbligatorie

1. Eseguire tutti i casi della checklist assegnabili al frontend.
2. Compilare per ogni caso `Esito` ed `Evidenza` senza modificare ID o risultato atteso.
3. Verificare almeno desktop, tablet e navigazione da tastiera per pagine, modal e drawer nuovi.
4. Verificare messaggi comprensibili per risposte `403`, `404`, `409` e `422`.
5. Verificare che dati sanitari, note riservate, token e dettagli tecnici non compaiano in toast, console o URL.
6. Confermare che le azioni non autorizzate siano nascoste e restino comunque bloccate dal backend.
7. Eseguire `npm run build` e riportare il risultato.

## Moduli da validare

- profilo, documenti, certificazioni e valutazioni professionisti;
- dashboard HR e idoneita consultiva ai turni;
- bacheca e circolari;
- calendario attivita e promemoria;
- media attivita e consenso;
- incidenti e segnalazioni;
- farmaci e somministrazioni;
- eventi sanitari, visite, esami e pronto soccorso.

## Criteri bloccanti

La release non e approvabile se si verifica almeno uno dei seguenti casi:

- accesso a dati di altra struttura o di un minore non assegnato;
- visualizzazione di contenuto clinico senza policy prevista;
- operazione dichiarata riuscita dopo risposta API di errore;
- upload o preview che aggira consenso, antivirus o policy documentale;
- perdita di dati, reset account, reset MFA o migrazione distruttiva;
- build frontend non riuscita.

## Risposta richiesta

Creare un solo file:

`docs/ux-handoff/responses/2026-08-20-197-v1.5.0-release-candidate-qa-response.md`

La risposta deve contenere:

- commit testato;
- ambiente e browser;
- riepilogo PASS/FAIL/BLOCKED/N/A;
- elenco degli ID non PASS con motivazione;
- bug corretti e file modificati;
- esito finale `APPROVATA`, `APPROVATA CON RISERVE` oppure `BLOCCATA`;
- risultato di `npm run build`.
